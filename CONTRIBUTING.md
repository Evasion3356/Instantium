# Contributing to Instantium

## Branch model

`master` is the release branch and must always be releasable. `develop` is the
shared integration branch. Actual releases are identified by a version update,
a validated release archive, and a matching Git tag; merging a pull request
does not publish a release by itself.

Create each change from an up-to-date `develop` on a short-lived branch:

```text
<github-user>/fix-<topic>
<github-user>/feat-<topic>
<github-user>/docs-<topic>
```

Open feature pull requests against `develop`. Do not push development commits
directly to `develop` or `master`, force-push shared branches, or mix unrelated
work in one pull request. After the integrated changes pass combined validation,
open one reviewed promotion pull request from `develop` to `master`.

## Local checkout

Keep Instantium in its own Git repository. In the shared Darktide workspace,
the authoritative checkout is:

```text
mods/active/Instantium/
```

Create `.source-path.local` from `.source-path.local.example` and point it to
your own decompiled Darktide `scripts` directory. The file is ignored and must
never be committed.

## Change workflow

1. Fetch `origin` and update local `develop` with a fast-forward pull.
2. Create a feature branch from that updated `develop`.
3. Source-trace changed Darktide or DMF contracts before implementation.
4. Make the smallest change that tests one stated hypothesis.
5. Validate changed runtime Lua and `.mod` files statically.
6. Test the affected game context and cleanup path when runtime behavior changes.
7. Inspect `git status`, `git diff`, and recent commits.
8. Stage only intended Instantium files and use a focused commit message.
9. Push the feature branch and open a pull request against `develop`.
10. Confirm the pull request acceptance criteria, then squash-merge to `develop`.
11. Validate the combined `develop` tree before promoting it to `master` in a
    separate pull request approved by the other maintainer.

Do not run Instantium and InstantHub together during runtime tests. Record the
Darktide build, settings, scenario, observed result, and untested contexts in
the pull request.

## Pull request acceptance

A pull request is ready to merge only when:

- The behavior and its motivation are clear.
- New or changed hooks and engine APIs are verified against current source.
- Package ownership and release paths cover disable, unload, transition, and
  failure or cancellation where applicable.
- Changed runtime Lua and `.mod` files pass syntax and LuaLS validation.
- Relevant runtime behavior is observed, or the missing runtime coverage is
  explicitly stated and accepted.
- Temporary probes, verbose logging, captures, generated bytecode, and local
  machine paths are absent.
- User-facing behavior and `CHANGELOG.md` are updated when appropriate.

## Release boundary

Merging a `develop` promotion to `master` means the source is considered
releasable. It does not mean that a public release has been created.

A release requires an explicit maintainer decision and must:

1. Start from a clean, reviewed `master` commit.
2. Update the version in `Instantium.mod` and `CHANGELOG.md` consistently.
3. Run the complete static and selected runtime release checks.
4. Build and inspect one archive rooted at `Instantium/`.
5. Record the archive SHA-256 and its source commit.
6. Create a matching signed or annotated version tag such as `v0.1.0` only
   after the archive has passed inspection.

The runtime payload consists of:

```text
Instantium/Instantium.mod
Instantium/scripts/mods/Instantium/**
```

`README.md` and `CHANGELOG.md` may be included as intentional user
documentation. Do not release `.git/`, `.github/`, `.source-path.local`,
`.source-path.local.example`, `AGENTS.md`, `CLAUDE.md`, `CONTRIBUTING.md`,
`GOAL.md`, tests, tools, captures, logs, generated bytecode, or files from any
other mod.

Pre-release builds must be labeled as such and must not reuse a stable version
tag. Rollback is the previous tagged release archive and source commit.
